SSR이 SEO에 좋다는 말,
반은 맞고 반은 틀렸다

조사일 2026-07-27 · 대상 yohanstudio.co (Next.js 16.2.4) · 코드 변경 0건 · 모든 수치는 라이브 사이트 직접 측정값

SSR은 우리 문제가 아니다. 이 사이트는 이미 페이지 18장 중 15장이 서버에서 완성된 HTML로 나간다. 진짜 문제는 목록 페이지 딱 3장 — /blog · /updates · /showroom 이 검색로봇 눈에는 백지로 보인다는 것.

핵심 1
축이 SSR이 아니다
"SSR이냐 SSG냐"가 아니라 서버가 보낸 HTML에 글이 들어있냐가 전부다. 우리가 쓰는 SSG는 SSR보다 열등하지 않다. 오히려 더 빠르다.
핵심 2
결함 3장, 실측 확인
/blog HTML에 글 링크 0건. /updates에 버전 표기 0건. /showroom은 9개 중 1개만.
핵심 3
손해는 AI 쪽이 더 크다
구글은 JS를 돌려서 결국 본다(늦게). ChatGPT·Claude·Perplexity 크롤러는 JS를 아예 실행 안 한다 → 영영 못 본다.

1먼저 개념부터 바로잡기

들은 말이 틀린 건 아닌데, 문장이 뭉개져 있다. 정확한 문장으로 바꾸면 이렇다.

❌ 들은 말: "SSR을 써야 SEO에 좋다"
✅ 정확한 말: "서버가 보낸 HTML에 글이 이미 들어있어야 검색에 좋다"

HTML을 언제 만드느냐로 방식이 4가지 갈리는데, 검색 관점에서 중요한 건 시점이 아니라 만드는 주체가 서버냐 브라우저냐다.

방식HTML을 언제·누가 만드나검색로봇이 받는 것SEO우리 사이트 예시
SSG
정적 생성		 배포할 때 서버가 미리 다 만들어 파일로 저장 완성된 글이 통째로 최상 /blog/[글], /design
ISR
주기적 재생성		 SSG와 같되, 정해둔 시간마다 서버가 다시 만듦 완성된 글이 통째로 최상 / 60초, /learning-log 1시간
SSR
요청 때 생성		 방문자가 들어올 때마다 서버가 즉석에서 완성된 글이 통째로 최상 /learning-log/[id]
CSR
브라우저가 그림		 서버는 빈 껍데기만 보내고 브라우저가 JS 돌려서 채움 빈 껍데기 나쁨 /blog 목록, /updates, /showroom 목록

즉 위 3개(SSG·ISR·SSR)는 SEO상 사실상 동급이다. 굳이 SSR로 바꿀 이유가 없고, 오히려 SSG가 더 빠르고 싸다. 문제는 4번째 줄 하나뿐이다.

"Server-side or pre-rendering is still a great idea because it makes your website faster for users and crawlers, and not all bots can run JavaScript." — Google Search Central, JavaScript SEO Basics · 마지막 문장이 이번 조사의 핵심이다
용어 1줄 풀이 — 크롤러/검색로봇: 사이트를 자동으로 읽어가는 프로그램. · 프리렌더: 방문자가 오기 전에 미리 HTML을 만들어두는 것. · 하이드레이션: 서버가 만든 HTML 위에 브라우저가 JS를 붙여 버튼이 눌리게 만드는 과정.

부수 발견 — 문서와 실제가 다름
CLAUDE.md 기술스택 표에 적힌 두 가지가 실제와 다르다. ① OG 이미지는 @vercel/og가 아니라 Next 내장 next/og를 쓴다(패키지 자체가 설치돼 있지 않음). ② sitemap은 next-sitemap이 아니라 네이티브 src/app/sitemap.ts다. 기능은 정상이니 급하진 않지만, 문서를 실제에 맞추는 게 좋다.

3결함 3장 — 증거

추측이 아니라 라이브 사이트에서 직접 받아본 HTML을 센 숫자다.

# 실제로 실행한 명령 (2026-07-27)
curl -sL https://yohanstudio.co/blog | grep -o 'href="/blog/[a-z0-9-]*"' | sort -u | wc -l
→ 0          # 글 링크가 한 개도 없음 (HTML 크기는 44,941 바이트)

curl -sL https://yohanstudio.co/updates | grep -o 'v[0-9]\+\.[0-9]\+\.[0-9]\+' | wc -l
→ 0          # 릴리즈 버전 표기 0건 (HTML 45,108 바이트)

curl -sL https://yohanstudio.co/showroom | grep -o 'href="/showroom/[a-z0-9-]*"' | sort -u | wc -l
→ 1          # 상단 대표 배너 1개만. 나머지 8개 프로젝트 누락

# 대조군 — 정상 페이지
curl -sL https://yohanstudio.co/blog/hello-world | grep -o '<h2' | wc -l
→ 2          # 본문 소제목 정상 포함 ✅

왜 이렇게 되나

세 페이지 다 똑같은 한 가지 패턴 때문이다. 목록을 그리는 컴포넌트가 주소창의 ?tag=... 값을 읽으려고 useSearchParams()를 쓰는데, 이 함수는 "방문자가 실제로 접속해야만" 값을 알 수 있다. 그래서 미리 만들어두는 단계에서는 그 부분을 통째로 포기하고 브라우저에 떠넘긴다.

1. 빌드목록 컴포넌트가 useSearchParams() 호출
→
2. 포기가장 가까운 Suspense 경계까지 프리렌더 중단
→
3. HTML그 자리에 대체물(fallback)만 남음 — 우리는 null, 즉 아무것도 안 남음
→
4. 브라우저JS 실행 후에야 목록이 그려짐
"If a route is prerendered, calling useSearchParams will cause the Client Component tree up to the closest Suspense boundary to be client-side rendered."

"This component passed as a fallback to the Suspense boundary will be rendered in place of the search bar in the initial HTML." — Next.js 공식 문서, useSearchParams (v16.2.12) · 즉 이건 버그가 아니라 설계된 동작이다. 우리가 fallback을 null로 둔 게 문제.

해당 위치 (참고용):

  • src/app/blog/page.tsx:74-76 → TagFilter.tsx:23
  • src/app/updates/page.tsx:83-85 → UpdatesFeed.tsx:29
  • src/app/showroom/page.tsx:103-105 → ProjectGrid.tsx:36
정직하게 짚을 뉘앙스 — 데이터가 HTML에 아예 없는 건 아니다. 페이지 소스 안쪽 <script> 덩어리(RSC 페이로드)에는 글 주소 문자열이 들어있다. 하지만 그건 링크도 아니고 읽히는 글도 아니다 — 로봇이 "이 페이지에서 저 페이지로 가는 길"로 인식하지 못한다. Vercel 문서도 "색인될 수도 있다" 정도로만 말한다. 기대면 안 되는 근거다.

6앞으로 직접 확인하는 법 학습

이게 이번 조사에서 가져갈 가장 실용적인 기술이다. 한 번 익히면 어떤 사이트든 30초 안에 판정할 수 있다.

함정부터. 브라우저에서 F12(개발자도구)로 보면 항상 정상으로 보인다. 개발자도구는 JS가 다 돌아간 후의 화면을 보여주기 때문이다. 검색로봇이 보는 건 그게 아니다.

보는 방법보이는 것로봇 관점에서
F12 개발자도구 → ElementsJS 실행 후 최종 화면❌ 판정 불가
Ctrl+U (페이지 소스 보기)서버가 보낸 원본 HTML✅ 이게 정답
터미널 curl서버가 보낸 원본 HTML✅ 이게 정답

가장 쉬운 방법 — 클릭 3번

  • 확인할 페이지에서 Ctrl+U
  • Ctrl+F 로 화면에 보이는 제목 한 줄을 검색
  • 안 나오면 → 그 내용은 로봇 눈에 없는 것

PowerShell로 세는 법 (윈도우 기본)

# /blog HTML에 글 링크가 몇 개나 들어있나
((Invoke-WebRequest "https://yohanstudio.co/blog").Content |
  Select-String 'href="/blog/[a-z0-9-]+"' -AllMatches).Matches.Count

# 정상 페이지와 비교해보면 차이가 바로 보인다
((Invoke-WebRequest "https://yohanstudio.co/blog/hello-world").Content |
  Select-String '<h2' -AllMatches).Matches.Count
기억할 한 문장 — "Ctrl+U 에서 안 보이면, 구글엔 늦게 보이고 AI 검색엔 아예 안 보인다."
