# 생일 축하 앱·우사기 세트 콘텐츠 브리프

> 상태: 서사 보강 · 사실 재검증 중 · MDX 작성 전
> 원칙: 요한스튜디오를 정본으로 삼고, 공개 가능한 사실과 증거만 사용한다.

## 1. 캠페인 구성과 용어

두 프로젝트를 한 글에 합치지 않는다.

- 생일 축하 앱은 **AI가 의도를 맞히지 못했을 때 제작 방식을 바꾼 과정**과 한 사람을 위한 경험 설계를 다룬다.
- 우사기 Windows 세트는 **릴스에서 본 아이디어를 실제 선물로 옮기고, 적용보다 원복까지 책임진 과정**을 다룬다.

공개 순서는 Studio 원문 → 쇼룸 사례 → 파생 콘텐츠다. 첫 공개에서는 요한스튜디오 글과 쇼룸만 연결한다. 공개용 빌더·오픈소스 저장소·다운로드 파일이 실제로 준비되기 전에는 GitHub, 데모, 다운로드 버튼을 만들지 않는다.

### 헷갈렸던 ‘생성기’ 구분

| 구분 | 정확한 이름 | 현재 상태 | 역할 |
|---|---|---|---|
| 이번 프로젝트에서 이미 만든 도구 | 웹 기반 콘티·상호작용 편집기 | 구현 완료 · 개인 프로젝트 내부 도구 | 장면·이미지·텍스트·행동·반응·BGM을 직접 배치하고 AI가 읽을 JSON을 만든다. |
| 나중에 공개할 수 있는 도구 | 생일 앱 빌더 | 아직 설계 전 | 사용자가 자기 사진·문구·장면을 넣고 미리 본 뒤 독립 실행 파일을 내보내는 범용 도구다. |

기존 문서의 ‘생일 축하 생성기’는 두 개념을 섞어 보여주므로 앞으로 쓰지 않는다. 공개판은 **생일 앱 빌더**로 부른다. 구현 형태는 브라우저에서 로컬로 편집하되, 결과는 서버 없이 실행되는 단일 HTML 또는 ZIP으로 내보내는 방향이 적합하다.

AI 도구를 처음 언급할 때는 **AI 코딩 에이전트(Codex·Claude Code 같은 도구)**라고 쓴다. 이후에는 AI 에이전트로 줄인다. 실제 역할은 과장하지 않는다. 요한이 콘티를 직접 구성했고, Codex는 구현을, Claude Code는 문서·프롬프트·브라우저 QA를 중심으로 맡았다.

## 2. 생일 축하 앱 제작기

### 확정 제목

**14장짜리 생일 앱을 친구 한 명을 위해 만들었다**

제목 아래 설명은 다음 방향으로 쓴다.

> 이미지 생성이 막히자 콘티 편집기를 직접 만들고, AI 코딩 에이전트와 함께 원하는 장면을 실제 노트북에서 끝까지 움직이게 만든 기록.

보조 제목 후보는 아래 두 개만 보관한다.

- 이미지 생성이 막히자 생일 앱 제작 도구부터 만들었다
- 빌드 성공이 아니라 실물 노트북 완주를 끝으로 잡았다

### 의도와 독자

AI나 바이브코딩에 관심은 있지만 개발 기술보다 **왜 이런 제작 방식을 택했는지**가 궁금한 사람을 위한 글이다. AI가 자동으로 완성해 준 성공담이 아니라, 의도가 어긋났을 때 사람이 직접 구조를 만들고 AI의 역할을 다시 배치한 사례로 보여준다.

이 글의 목적은 개인용 앱을 배포하는 것이 아니다. 요한스튜디오가 작은 아이디어를 실제 경험으로 바꾸고, 결과가 나올 때까지 제작 방식 자체를 고칠 수 있는 곳이라는 인상을 남기는 것이 우선이다.

### 글을 끌고 갈 질문

**AI가 원하는 이미지를 만들지 못할 때 프롬프트를 계속 고칠 것인가, 아니면 내가 의도를 전달하는 제작 방식을 바꿀 것인가?**

### 핵심 메시지

- 한 번만 쓰는 선물도 이야기와 실패 조건을 설계하면 하나의 제품이 된다.
- AI 이미지가 의도를 맞히지 못하자, 프롬프트 반복 대신 내가 직접 조정할 콘티 편집기를 만들었다.
- 완성은 코드나 이미지 한 장이 나온 순간이 아니라, 친구가 실제 노트북에서 마지막 장면까지 경험할 수 있는 상태다.

### 첫 문단 방향

> 처음에는 우사기 애니메이션으로 시작해 짧은 게임을 지나 편지로 끝나는 생일 선물을 만들고 싶었다. 문제는 머릿속 장면이 이미지 생성 결과에 잘 나오지 않았다는 것이다. 컷마다 분위기가 달라지고, 달력 숫자는 뭉개졌고, 남은 시간 안에 모든 장면을 다시 뽑는 방식으로는 끝이 보이지 않았다.

다음 문단에서 바로 결과를 말한다.

> 그래서 이미지를 더 뽑는 대신, 내가 장면을 직접 배치하고 AI 코딩 에이전트가 그 상태를 읽을 수 있는 콘티 편집기를 앱 안에 만들었다. 그 편집기를 거쳐 최종 상영본은 14장이 됐다.

### 글의 흐름

1. 친구가 좋아하는 우사기로 애니메이션 → 탐색 게임 → 편지까지 이어지는 생일 경험을 만들고 싶었다.
2. 실제로 스토리보드를 짜보니 예쁜 화면보다 장면 사이의 이유와 반응을 연결하는 일이 더 어려웠다.
3. AI 이미지 생성은 날짜·숫자·캐릭터 일관성·복합 동작에서 의도와 어긋났고, 품질과 마감 시간 모두 불리해졌다.
4. 4막 16씬, 3막 7씬 등 여러 구조를 거친 뒤 애니메이션과 방 탐색을 그대로 밀어붙이지 않고 이미지·짤 중심의 상영 구조로 바꿨다.
5. 화면을 말로만 설명하는 대신, 앱 안에 웹 기반 콘티·상호작용 편집기를 만들었다.
6. 요한이 이미지와 문구를 직접 놓고, 장면마다 처음 보이는 것 → 친구가 할 행동 → 성공·실패 반응 → 웃음 포인트를 입력했다.
7. 편집기는 좌표와 의도를 JSON으로 보여줬고, AI 코딩 에이전트가 이를 읽어 실제 상영 런타임을 구현·수정했다. Codex와 Claude Code는 구현과 QA 역할을 나눴다.
8. 첫 초안은 브라우저 저장소에만 남아 다른 노트북에서 사라질 수 있었다. 이를 Git에 고정된 공식 콘티와 안정적인 에셋 ID 구조로 바꿨다.
9. 사용자가 예상과 다르게 행동해도 멈추지 않도록 힌트, 대체 동작, 시간 기반 자비 경로를 넣었다.
10. 마지막 우사기 Windows 선물 장을 더해 공식 상영본은 14장이 됐고, 편지에서 자동으로 넘어가던 흐름도 직접 선택 방식으로 다시 고쳤다.
11. 새 클론 재현과 전체 흐름 자동 검사를 거친 뒤, 2026년 8월 2일 실물 노트북에서 처음부터 끝까지 리허설했다.
12. 실제로 친구에게 보여준 순간과 반응을 확인된 사실만으로 덧붙여 이야기를 닫는다.
13. 얼굴·실명·사적인 문장과 캐릭터 자산이 들어간 원본은 공개하지 않고, 공개판은 별도의 생일 앱 빌더로 다시 만든다.

글 안에서 모든 버그를 나열하지 않는다. **이미지 생성의 한계 → 편집기 제작 → 브라우저 초안이 전달되지 않은 실패 → 실물 완주** 네 전환점만 깊게 다룬다.

### 실제 상영 후기

요한은 2026년 8월 2일 친구에게 앱을 실제로 보여줬다. 친구가 예상보다 크게 감동한 모습에 요한도 놀랐고, 친구는 나중에 울었다고 전했다.

정확한 첫마디, 가장 크게 반응한 장면, 중간에 막힌 행동은 기록되지 않았다. 없는 세부 장면을 보충하지 않고 **요한이 예상한 것보다 감정이 크게 전달됐다는 사실**만 회고로 쓴다. 친구의 말을 따옴표로 꾸미지 않고 “친구는 나중에 울었다고 말했다”라고 간접 인용한다.

### 증거와 이미지 역할

| 글 구간 | 필요한 증거 | 공개 처리 |
|---|---|---|
| 최종 결과 | 개인정보 없는 실물 노트북 완주 영상 | 공개용 화면으로 재촬영하거나 안전 구간만 편집 |
| 이미지 생성이 막힌 지점 | 실패 유형을 설명하는 도식 | 우사기 원본 대신 숫자·일관성·동작 문제를 일반화 |
| 제작 방식을 바꾼 지점 | 콘티 편집기 화면과 구조화된 JSON | 실명·편지·우사기 자산을 대체한 재현 화면 사용 |
| 구현·QA 반복 | 요한 → 편집기 → AI 에이전트 → 브라우저 검증 흐름도 | 실제 역할만 적고 도구 로고 나열은 피함 |
| 전달과 반응 | 요한의 실제 상영 후기 | 친구 사진 없이 간접 인용으로 기록 |
| 검증 | 공식 14장·새 클론·실물 리허설 기록 | E2E 개수는 최신 재실행 전까지 숫자로 쓰지 않음 |

### 공개 경계와 CTA

- 현재 앱의 소스, 데모, 원본 파일은 비공개로 유지한다.
- 글 하단 CTA는 생일 축하 앱 쇼룸 사례로 연결한다.
- 생일 앱 빌더가 실제로 만들어진 뒤에만 빌더·GitHub 링크를 추가한다.
- 친구 사진은 사용하지 않는다. 상영 반응은 확인된 간접 인용만 사용한다.

## 3. 우사기 Windows 선물 세트 제작기

### 확정 제목

**릴스에서 본 우사기 커서, 직접 Windows 선물 세트로 만들었다**

기술적인 보조 제목은 다음으로 잡는다.

> 커서·휴지통·폴더·작업 표시줄을 바꾸고, 설치보다 원복을 먼저 검증한 개인 선물 제작기.

보조 제목 후보는 하나만 보관한다.

- 커서·휴지통·폴더를 바꾸고, 설치보다 원복을 먼저 검증했다

### ‘25종’ 정정

25종은 현재 산출물과 맞지 않는 오래된 README 수치다. 같은 README 표의 합계도 21개였고, 이후 작업 표시줄 아이콘이 추가돼 현재 Git에서 확인되는 최종 출력 파일은 **22개**다.

- 화살표 커서 2개
- 대기 애니메이션 1개
- 휴지통 12개: 빈 상태·가득 찬 상태 × 귀 유무 × 웃음·울음·혀 빼꼼
- 폴더 6개: 귀 유무 × 웃음·울음·혀 빼꼼
- 작업 표시줄 아이콘 1개

22개는 서로 다른 테마 22종이 아니라 **한 세트를 구성하는 출력 파일 수**다. 제목에는 숫자를 쓰지 않고 실제로 바뀌는 대상을 말한다.

### 의도와 독자

귀여운 결과물에 끌리는 사람과, 작은 커스터마이징 도구도 안전하게 만들어야 한다고 생각하는 제작자를 함께 겨냥한다. 시작은 릴스에서 본 우사기 커서였지만, 글의 중심은 이를 친구가 실제로 쓸 수 있는 Windows 선물 세트로 확장한 과정이다.

현재 우사기 파일을 공개 배포하거나 다운로드를 유도하는 글이 아니다. 캐릭터 자산과 무관하게 재사용할 수 있는 적용·백업·복구 노하우를 포트폴리오로 남긴다.

### 글을 끌고 갈 질문

**커서 하나를 따라 만들기 시작했는데, 어디까지 만들어야 ‘친구가 실제로 써도 되는 선물’이 되는가?**

### 핵심 메시지

- 릴스의 짧은 아이디어를 커서·휴지통·폴더·작업 표시줄이 연결된 실제 Windows 세트로 확장했다.
- 귀여운 화면보다 중요한 건 친구의 기존 설정과 파일을 망가뜨리지 않는 것이다.
- 꾸미기는 적용에서 끝나지 않는다. 원래 환경으로 정확히 돌아갈 때 비로소 완성이다.

### 첫 문단 방향

> 친구가 좋아하던 우사기 커서 릴스를 보고 ‘이 정도면 나도 직접 만들 수 있지 않을까’ 생각했다. 처음에는 커서 하나가 목표였다. 그런데 실제 선물로 주려니 휴지통과 폴더, 작업 표시줄까지 한 세트처럼 보여야 했고, 무엇보다 마음에 들지 않을 때 원래 Windows로 돌아갈 수 있어야 했다.

다음 문단에서 가장 강한 실패를 예고한다.

> 적용은 됐지만 원복 버튼을 눌러도 우사기가 남는 문제가 생겼다. 반복 적용 과정에서 이미 바뀐 상태를 원본이라고 다시 저장한 것이 원인이었다.

### 글의 흐름

1. 친구가 릴스에서 본 우사기 커서를 좋아했고, 요한은 직접 만들 수 있겠다는 생각에서 시작했다.
2. 커서 하나를 흉내 내는 데서 멈추지 않고 휴지통·폴더·작업 표시줄까지 같은 표정 체계로 확장했다.
3. 커서와 아이콘은 Windows가 실제로 읽을 수 있는 CUR·ANI·ICO 형식과 여러 해상도로 구성했다.
4. 중간 결과는 합성 데모 GIF·MP4와 이미지로 확인하며 선물의 전체 인상을 다듬었다.
5. 반복 적용 과정에서 이미 우사기로 바뀐 상태가 새 백업이 돼, 복구해도 우사기로 돌아오는 결함을 발견했다.
6. 최초의 깨끗한 상태를 한 번만 보존하고 덮지 않는 pristine backup 방식으로 복구 구조를 다시 만들었다.
7. 적용·재적용·복구를 격리 환경에서 왕복 검증하고, 최종 출력 파일 22개가 Windows API에서 로드되는지 확인했다.
8. 생일 앱의 마지막 장에서 우사기 세트를 별도 선물로 전달했다.
9. 친구 노트북에서 전체 원복까지 확인한 사실을 결과 구간에 넣고, 친구 사진은 사용하지 않는다.
10. 우사기 원본 자산은 공개하지 않고, 공개판은 사용자가 자기 캐릭터를 넣는 Windows 캐릭터 테마 빌더로 분리한다.

### 실제 적용과 원복 확인

요한은 친구 노트북에서 전체 원복까지 확인했다고 2026년 8월 3일 다시 확인했다. 저장소에 남은 격리 환경 검증과 별개로, 실제 수령인 환경에서도 원래 상태로 돌아온 사실을 후기와 쇼룸 결과에 사용할 수 있다.

사진 공개 동의는 받지 않았고, 굳이 받을 필요도 없다. 친구 사진이나 개인 바탕화면 대신 개인정보가 없는 격리 Windows에서 실제 우사기 세트의 적용 → 전체 원복 화면과 시스템 도식으로 결과를 증명한다. 캐릭터의 화면 노출은 허용하지만 PNG·CUR·ANI·ICO·ZIP과 저장소는 공개하지 않는다. 기존 합성 데모는 내부 참고로만 둔다. 실제로 계속 사용하는 세부 항목과 Windows 버전은 확인되지 않았으므로 해당 내용은 단정하지 않는다.

### 증거와 이미지 역할

| 글 구간 | 필요한 증거 | 공개 처리 |
|---|---|---|
| 시작 | 릴스에서 영감을 받은 상황을 보여주는 재구성 컷 | 원본 릴스 무단 재업로드 대신 요한의 문장과 직접 촬영 사용 |
| 결과 | 커서·휴지통·폴더·작업 표시줄이 바뀌는 짧은 데모 | 격리 Windows에서 실제 적용·원복만 촬영. 화면 노출만 허용하고 원본 파일은 비공개 |

| 실제 환경 검증 | 친구 노트북 전체 원복 확인 | 사진 없이 요한의 회고와 안전한 원복 도식으로 전달 |

### 공개 경계와 CTA

- 우사기 PNG, CUR·ANI·ICO, 설치 ZIP과 현재 저장소는 공개하지 않는다.
- 기존 합성 데모는 저장소 권리 고지에 따라 공개하지 않는다. 새 공개 영상은 격리 Windows에서 실제 적용·원복 화면만 직접 촬영한다.
- 우사기 세트의 화면 노출과 자산 배포를 구분한다. PNG·CUR·ANI·ICO·ZIP·저장소·다운로드 링크는 공개하지 않는다.
- 글 하단 CTA는 우사기 Windows 세트 쇼룸 사례로 연결한다.
- 범용 빌더와 권리 정리된 샘플이 실제로 만들어진 뒤에만 GitHub·다운로드 링크를 추가한다.

## 4. 쇼룸 사례 정보 구조

쇼룸은 제작 일지를 날짜순으로 길게 보여주는 곳이 아니다. 방문자는 먼저 **무엇을 왜 만들었고, 실제로 됐는지**를 확인한 뒤 과정에 관심을 가진다. 날짜는 프로젝트 목록 정렬과 사례 안의 짧은 타임라인에만 사용한다.

Studio의 현재 쇼룸은 최신 프로젝트를 dateCreated 내림차순으로 정렬한다. 이 기준은 유지하되, 상세 페이지는 **결과 먼저, 이유와 과정은 그다음**으로 바꾼다.

### 위에서 아래로 읽히는 순서

| 순서 | 방문자가 묻는 질문 | 보여줄 내용 | 시각 자료 |
|---|---|---|---|
| 1. Hero | 그래서 뭘 만들었나? | 결과가 들어간 제목, 한 문장 요약, 최종 상태 | 실제 결과 영상 또는 대표 이미지 |
| 2. Snapshot | 누구를 위해, 언제, 무슨 역할로? | 대상·기간·역할·상태 | 짧은 정보 카드 |
| 3. Outcome | 실제로 됐나? | 검증된 결과와 사용 증거 | 실물 사용 장면, 전후 비교, 핵심 수치 |
| 4. Why | 왜 이걸 만들었나? | 시작 계기, 해결할 문제, 성공 조건 | 맥락 사진 또는 한 장짜리 도식 |
| 5. Turning points | 무엇이 계획을 바꿨나? | 핵심 실패와 방향 전환 3~4개 | 과정 캡처, 짧은 타임라인 |
| 6. Decisions | 왜 그렇게 만들었나? | 선택·이유·검토한 대안·감수한 점 | 결정 카드 또는 구조도 |
| 7. Proof | 어떻게 확인했나? | 자동 검사·실물 리허설·실제 사용 | 테스트 기록, 영상, 문서 증거 |
| 8. Responsibility | 무엇을 공개하지 않나? | 개인정보·저작권·복구 책임 | 경계 안내 카드 |
| 9. Limits | 아직 무엇이 남았나? | 한계와 다음 개선 | 텍스트 중심 |

핵심은 모든 섹션이 **왜?**에 답하게 하는 것이다. 단순히 “편집기를 만들었다”가 아니라 “이미지 생성만으로 의도를 고정할 수 없어서 만들었다”고 쓴다. “pristine backup을 썼다”가 아니라 “반복 적용이 원본 백업을 오염시켰기 때문에 최초 상태를 따로 지켰다”고 쓴다.

### 생일 축하 앱 쇼룸 매핑

- 제목: AI 이미지가 막히자 콘티 편집기부터 만든 14장 생일 앱
- Hero 결과: 개인정보 없는 최종 흐름 10~15초 영상
- 한 문장 Why: 친구 한 명에게 한 번 보여줄 선물을, 원하는 장면과 반응까지 직접 통제하기 위해 만들었다.
- Outcome: 공식 14장 고정, 새 클론 재현, 실물 노트북 처음부터 끝까지 리허설 완료
- 가장 강한 전환점: 이미지 생성 반복 중단 → 콘티 편집기 제작 → 브라우저 초안 전달 실패 → Git 정본 고정
- 역할: 이야기 구조, 콘티 직접 배치, AI 에이전트 지휘, 구현 검수, 실물 리허설
- 실제 반응: 친구가 예상보다 크게 감동했고 나중에 울었다고 전한 후기
- 개인정보 고지: 얼굴·실명·개인 메시지·원본 사진은 비공개이며 공개용 대체 자산만 사용
- 등급: 실제 반응은 확보했다. 안전한 Hero 증거가 준비될 때까지 standard, 준비 후 flagship 후보

### 우사기 Windows 선물 세트 쇼룸 매핑

- 제목: 릴스 속 우사기 커서를 Windows 선물 세트로 만든 과정
- Hero 결과: 커서 이동 → 휴지통 변화 → 폴더 → 작업 표시줄 → 원복을 한 번에 보여주는 짧은 영상
- 한 문장 Why: 친구가 좋아한 커서를 실제로 쓸 수 있는 선물로 만들되, 원래 Windows 상태를 해치지 않기 위해 만들었다.
- Outcome: 최종 출력 파일 22개 로드 확인, 격리 환경 적용·재적용·복구 검증, 친구 노트북 전체 원복 확인
- 가장 강한 전환점: 커서 한 개 → 세트 확장 → 원복해도 우사기가 남는 결함 → pristine backup
- 역할: 자산 구성, Windows 형식 변환, 설치·백업·복구 설계, 검증, 전달 패키지 제작
- 실제 환경: 친구 노트북에서 전체 원복까지 확인. 사진은 사용하지 않음
- 저작권 고지: 우사기 자산은 개인용이며 원본 파일·설치 패키지·저장소를 공개하지 않음
- 등급: 전체 원복은 확인됐다. 공개 가능한 Hero 증거와 권리 범위가 정리될 때까지 standard 유지

### 현재 쇼룸 구현에서 보강할 점

현재 CaseStudyDetails는 문제 → 제약 → 수치 → 결정 → 검증 → 증거 순이다. 새 사례를 쓰기 전에 아래 변경을 별도 구현 단위로 잡는다.

- Hero 바로 아래에 Outcome과 대표 증거를 먼저 노출
- 문제 정의 제목을 ‘왜 만들었나’로 바꿔 일반 독자도 바로 이해하게 함
- 날짜 나열 대신 방향이 바뀐 사건만 담는 Turning points 타임라인 추가
- 이미지마다 예쁘게 보이는 역할이 아니라 전달해야 할 정보를 지정
- informative 이미지는 그 의미를 설명하는 대체 텍스트와 인접 문장을 함께 작성
- 개인 선물 사례에 맞는 완료 상태 문구를 추가해 ‘출시·운영 검증’이라는 과한 표현을 피함

상세 기준과 외부 근거는 RESEARCH.md의 쇼룸 사례 섹션을 따른다.

## 5. MDX 작성 게이트

아래 조건이 충족되면 두 글의 MDX 초안을 만든다.

- FACT_SHEETS와 충돌하는 표현이 없다.
- 생일 앱의 실제 친구 반응은 간접 인용으로만 사용한다.
- 우사기 친구 사진은 사용하지 않고 전체 원복 확인과 안전한 재현 증거를 사용한다.
- 첫 세 문단 안에 실제 실패 또는 예상과 달랐던 문제가 나온다.
- 결과를 뒷받침하는 실제 증거가 최소 하나 정해져 있다.
- 개인정보와 저작권 자산의 공개 범위가 문장으로 명시되어 있다.
- 존재하지 않는 데모·GitHub·다운로드 링크를 넣지 않는다.
- 초안은 반드시 published false로 시작한다.
